# Repository health

## First screen

The first screen should answer, in this order:

1. What is this?
2. Who is it for?
3. What result can I get?
4. What is its honest maturity or limitation?
5. What is the shortest verified command?

Use one project identity asset, a small set of factual badges, a one-sentence thesis, and one primary action. Do not put contributor administration before user comprehension.

## README structure

Prefer the smallest structure that serves the project:

- purpose and boundary;
- quick start with a verified result;
- installation alternatives;
- behavior or architecture only where needed;
- safety, privacy, or evidence limits;
- project status and compatibility;
- help, contributing, security, and license links.

GitHub generates a table of contents from headings. Avoid a manual table of contents unless the document is unusually long or another renderer requires it.

## Bilingual repositories

- Keep one default README and one clearly linked translation.
- Match claims, commands, versions, limitations, and section coverage.
- Translate prose, labels, and alt text; preserve code, paths, identifiers, and product names.
- Treat semantic parity as a release check, not a one-time translation task.

## Community and trust surfaces

Check whether the repository genuinely needs and maintains:

- `LICENSE`
- `SECURITY.md`
- `CONTRIBUTING.md`
- `CODE_OF_CONDUCT.md`
- `SUPPORT.md`
- issue forms and pull-request template
- `CHANGELOG.md` or release notes
- private vulnerability reporting

Do not create dead support channels, empty roadmaps, fake governance, or templates the maintainer will not use.

## Repository metadata

Verify live rather than infer:

- concise description;
- relevant search topics;
- homepage or documentation URL when one exists;
- current default branch and latest release;
- CI status and supported runtime matrix;
- social preview image;
- community profile and security reporting state.
