# Evaluation rubric

Use this after implementation. Record `Pass`, `Partial`, `Fail`, or `Not applicable` with evidence.

## Comprehension

- A new visitor can state the project's purpose and audience from the first screen.
- The boundary between implemented behavior and aspiration is explicit.
- Terminology is consistent across README, package metadata, manifests, and releases.

## Onboarding

- One copyable command reaches a verified result.
- Requirements and supported clients are accurate.
- Installation alternatives are ordered by user value, not maintainer preference.
- Failure and help paths exist where real users need them.

## Trust

- Badges resolve to real workflows, releases, licenses, or factual compatibility.
- Benchmarks show scope, sample size, limitations, and non-guarantees.
- Security and privacy boundaries match actual behavior.
- Contribution, support, and conduct files point to maintained channels.

## Visual craft

- The visual direction has a name and a reason tied to the project.
- One element is memorable; the rest supports scanning.
- Light/dark behavior, narrow widths, contrast, alt text, and reduced-motion needs are handled where applicable.
- Typography, spacing, radii, line weights, and color accents form one system.
- Visual assets were rendered and inspected, not accepted from source code alone.

## Repository mechanics

- Local links and image paths resolve.
- JSON/YAML/SVG and issue forms parse.
- Tests, CI, package contents, plugin/Skill validation, and secret scanning pass as applicable.
- The final diff contains no unrelated user work or private artifacts.
- The public page and installation path were tested after merge.

## Stop line

Stop when every applicable high-impact item passes and remaining partial items have lower value than their maintenance cost. Do not optimize for a score by adding unused files or decorative assets.
